# Devcontainer test harness landscape

Research for [#26](https://github.com/dbarjs/agent-devcontainer/issues/26), part of map [#20](https://github.com/dbarjs/agent-devcontainer/issues/20). Researched 2026-08-13.

Question: what tooling best fits a three-tier automated test suite for this repo (images, template, dotfiles, adc CLI) in GitHub Actions?

- **Tier 1 — fast static, every PR**: lint/unit-test the `cli/adc` zsh CLI, validate `templates/devcontainer.json`, syntax-check `dotfiles/sheldon/plugins.toml` and `dotfiles/starship.toml`.
- **Tier 2 — container assertions**: against a built image, check binaries/versions, OCI `devcontainer.metadata` label and volume metadata, warning-free interactive zsh, `adc doctor`.
- **Tier 3 — e2e**: boot the real template with the devcontainer CLI and run a requirements checklist inside the live container.

Existing baseline in this repo: `.github/scripts/smoke-test.sh` (plain `docker run` + `docker inspect` assertions, run post-publish per image by `.github/workflows/publish.yml`). All version/maintenance claims below are as of 2026-08-13; local experiments were run on this machine (zsh 5.9, sheldon 0.8.5, starship 1.25.1, @devcontainers/cli 0.88.0).

## How the devcontainers org tests its own artifacts

The upstream pattern is worth copying because all three official repos (images, features, templates) converge on the same idiom: **build → `devcontainer up` with an `--id-label` handle → `devcontainer exec` a `test.sh` that sources a helper lib of `check` functions → `reportResults`**.

### devcontainers/images

- One `smoke-<image>.yaml` workflow per image (e.g. [`smoke-base-debian.yaml`](https://github.com/devcontainers/images/blob/main/.github/workflows/smoke-base-debian.yaml)), path-filtered on `src/<image>/**`, calling a composite action [`.github/actions/smoke-test`](https://github.com/devcontainers/images/blob/main/.github/actions/smoke-test/action.yaml).
- [`build.sh`](https://github.com/devcontainers/images/blob/main/.github/actions/smoke-test/build.sh): `npm install -g @devcontainers/cli`, `devcontainer build --image-name <image>-test-image --workspace-folder src/<image>/`, then `devcontainer up --id-label test-container=<image> --workspace-folder src/<image>/`.
- [`test.sh`](https://github.com/devcontainers/images/blob/main/.github/actions/smoke-test/test.sh): `devcontainer exec --id-label ... /bin/sh -c 'cd test-project && ./test.sh'`, then `docker rm -f` by label.
- Each image ships `src/<image>/test-project/` with a `test.sh` checklist and [`test-utils.sh`](https://github.com/devcontainers/images/blob/main/src/python/test-project/test-utils.sh) defining the helper vocabulary: `check <label> <cmd...>` (accumulates failures in an array), `check-version-ge`, `checkMultiple <label> <minimumPassed> <exprs...>`, `checkOSPackages`, `checkCommon` (non-root user, locale, zsh, etc.), and `reportResults` (prints failed labels, exits non-zero).
- A concrete checklist ([python `test.sh`](https://github.com/devcontainers/images/blob/main/src/python/test-project/test.sh)): `source test-utils.sh vscode; checkCommon; check "python" python --version; check "pipx" pipx --version; ...; reportResults`.

### devcontainers/features — `devcontainer features test`

- The CLI has a built-in harness, documented in [devcontainers/cli `docs/features/test.md`](https://github.com/devcontainers/cli/blob/main/docs/features/test.md): `test/<feature>/test.sh` (required), optional `scenarios.json` (scenario name → devcontainer.json snippet, with a sibling `<name>.sh` run after build), optional duplicate-install idempotency tests. Flags: `-f <feature>`, `-i/--base-image`, `--skip-scenarios`, `--skip-autogenerated`, `--skip-duplicated`.
- Test scripts `source dev-container-features-test-lib`, which provides exactly `check <LABEL> <cmd...>` and `reportResults` — e.g. [features `test/node/test.sh`](https://github.com/devcontainers/features/blob/main/test/node/test.sh).
- CI: [`test-all.yaml`](https://github.com/devcontainers/features/blob/main/.github/workflows/test-all.yaml) runs a matrix of every feature × a set of base images, each job a `devcontainer features test -f <feature> -i <baseImage>` invocation.
- **Fit here**: this harness is feature-shaped (it injects a feature onto a base image). This repo ships images + a template, not features, so the *library idiom* transfers but the `features test` command itself does not.

### devcontainers/templates

- [`test-pr.yaml`](https://github.com/devcontainers/templates/blob/main/.github/workflows/test-pr.yaml): path-filter changed templates → substitute `${templateOption:...}` defaults → copy `test/<template>/` + shared `test-utils.sh` into the src tree → `devcontainer up --id-label test-container=<template>` → `devcontainer exec ... ./test.sh`. Same idiom again.

## Tier 3 — e2e with the devcontainer CLI

### @devcontainers/cli mechanics relevant to CI

- Current version 0.88.0 (npm, last publish 2026-07-22; verified via `npm view @devcontainers/cli`).
- `devcontainer up` reuses an **existing** container found by `--id-label` — per `devcontainer up --help` (verified on 0.88.0): id-labels "will be set on the container and used to query for an existing container. If no --id-label is given, one will be inferred from the --workspace-folder path". `--remove-existing-container` recreates; `--expect-existing-container` asserts reuse; `--cache-from`/`--cache-to` pass through to the build. This is how upstream shares one live container between the `up` step and later `exec` steps.
- Prebuild interaction: a devcontainer.json that references a prebuilt `image` only triggers an extend-build when features/metadata require it; for this repo's images the DinD feature and metadata are baked at publish time, so `up` on the *template* (which is `"image": ghcr.io/...` only) pulls and starts without rebuilding. `devcontainer build`/`up` accept `--cache-from`/`--cache-to` (buildx cache destinations) and `build` accepts `--platform`/`--push`.
- `devcontainer read-configuration --workspace-folder <dir>` parses and resolves the JSONC config — verified locally against `templates/devcontainer.json` (exit 0, resolved JSON on stdout); it is the natural tier 1 validity check too (see below).

### devcontainers/ci GitHub Action

- [`action.yml`](https://github.com/devcontainers/ci/blob/main/action.yml) (inputs verified against source): `imageName`, `imageTag`, `platform`, `configFile`, `runCmd`, `push`, `cacheFrom`/`cacheTo`/`noCache`, `env`, `useNativeRunner`, `runCmdOutput`. Internally it installs @devcontainers/cli and shells out to `devcontainer build` / `up` / `exec` — the same commands available directly.
- Multi-platform ([`docs/multi-platform-builds.md`](https://github.com/devcontainers/ci/blob/main/docs/multi-platform-builds.md)): QEMU or a native-runner matrix with `useNativeRunner: true` — but that path requires `push: always`, and "`runCmd` ... will only be run on the architecture of the system the build is running on".
- Maintenance: slow-moving — latest release v0.3.1900000450 dates to 2024-06-01 ([releases](https://github.com/devcontainers/ci/releases)), though the repo still received pushes through 2026-06; consumers pin `devcontainers/ci@v0.3`.
- **Fit here**: the action is a thin wrapper around commands this repo already runs directly in `publish.yml`. Calling the CLI directly keeps the workflow one abstraction shallower and reuses the exact commands developers run locally; the action's main add (build+push+runCmd in one step) duplicates what `publish.yml` already does with more control.

### What the tier 3 requirements checklist looks like

Practiced form (upstream `test-project` pattern, adapted):

```bash
# .github/tests/e2e/test.sh — runs INSIDE the live container via devcontainer exec
source test-utils.sh   # check / checkMultiple / reportResults, vendored ~30 lines
check "zsh is login shell" bash -c 'getent passwd vscode | grep -q /bin/zsh'
check "history volume mounted" mountpoint -q /home/vscode/.local/state/history
check "claude bootstrap ran" test -x /home/vscode/.local/bin/claude
check "docker-in-docker up" docker info
check "adc doctor" bash -c 'adc doctor; [ $? -le 1 ]'   # agent/gh checks legitimately fail in CI — assert on specific lines instead
reportResults
```

driven from the runner by:

```bash
devcontainer up --workspace-folder "$tmp_project" --id-label ci-e2e=agent-devcontainer
devcontainer exec --workspace-folder "$tmp_project" --id-label ci-e2e=agent-devcontainer \
  /bin/sh -c 'cd /workspaces/*/; ./.ci/test.sh'
```

Two e2e realities specific to this repo: (a) the template's image carries baked `devcontainer.metadata` — `up` will apply the volume mounts, `onCreateCommand` (claude-bootstrap) and DinD entrypoint, which is exactly what tier 3 exists to prove and what no `docker run` test can cover; (b) `adc doctor` in CI has no forwarded SSH agent and no gh auth, so the e2e assertion should be "doctor runs, reports the expected pass/fail shape", not "all checks pass".

## Tier 2 — container assertion tools

### container-structure-test (GoogleContainerTools)

- Test types ([README](https://github.com/GoogleContainerTools/container-structure-test)): `commandTests` (setup/teardown, expectedOutput/expectedError regexes, exitCode), `fileExistenceTests`, `fileContentTests`, and `metadataTest` covering `labels` (exact or `isRegex`), `envVars`, `entrypoint`, `cmd`, `exposedPorts`, `volumes`, `workdir`, `user`.
- Drivers: `docker` (default, needs daemon, all test types) or `tar` (no daemon, **no commandTests**). Commands are exec'd directly, not via a shell — shell logic must be wrapped `zsh -ilc '...'` style, which works for the warning-free-zsh check.
- Multi-arch: `--platform` flag selects a platform from a multi-arch manifest (default `linux/amd64`); running arm64 commandTests on amd64 still depends on QEMU/binfmt since commands execute. Release binaries include linux/darwin arm64.
- Output: text/json/**junit** via `--test-report`.
- Maintenance: v1.22.1 (2025-12-16); README states verbatim it "is not an officially supported Google project, and is currently in maintainence mode".
- Limitation that bites here: `metadataTest.labels` matches the label **value as a string/regex** — asserting on fields inside the `devcontainer.metadata` JSON array means brittle regexes; `docker inspect | jq` is strictly better for that check.

### goss / dgoss

- goss ([README](https://github.com/goss-org/goss), [gossfile docs](https://github.com/goss-org/goss/blob/master/docs/gossfile.md)): declarative YAML checks for commands (exit-status/stdout/stderr), files, packages, processes, users, ports, HTTP, plus a gjson matcher; outputs include documentation/json/**junit**/tap. README speed claim: "small-medium test suites are near instantaneous", single <10 MB binary.
- dgoss ([README](https://github.com/goss-org/goss/blob/master/extras/dgoss/README.md)) starts the container, injects the goss binary + gossfiles (volume-mount by default), optionally waits on `goss_wait.yaml`, and runs goss **inside the running container** — so the container must stay alive (`sleep infinity` for an image whose CMD exits), and the goss binary must be a **Linux binary matching the container arch** (arm64 released: `goss_0.4.10_linux_arm64.tar.gz`). Testing both arches means managing two binaries.
- goss runs inside the container, so it **cannot see image config at all** — no label/volume/entrypoint assertions; `docker inspect` remains host-side.
- Maintenance: v0.4.10 (2026-07-26), actively maintained.

### Plain `docker run` + `docker inspect` script (status quo)

`.github/scripts/smoke-test.sh` already covers tier 2's checklist: toolchain versions via `docker run ... zsh -ilc`, warning-free interactive startup (capture output, assert empty — neither CST's `excludedOutput` nor goss expresses "no output at all" as directly), adc presence, and `devcontainer.metadata` label content via `docker inspect` + `jq`/`grep`. What the dedicated tools would add is a declarative catalog and junit reporting; what they cost is a pinned extra binary, a new config format, arch bookkeeping (goss), and — for CST — betting on a maintenance-mode tool. Neither adds assertion power for the checks that matter most here (metadata JSON, empty-output zsh startup).

## Tier 1 — static checks

### shellcheck and zsh

- shellcheck does **not** support zsh, by design: a `#!/usr/bin/env zsh` shebang triggers [SC1071](https://github.com/koalaman/shellcheck/wiki/SC1071) — "ShellCheck only supports sh/bash/dash/ksh scripts. Sorry!" — and the [man page](https://github.com/koalaman/shellcheck/blob/master/shellcheck.1.md) lists `--shell` values as `sh, bash, dash, ksh, busybox` only. The "support zsh" issue ([koalaman/shellcheck#809](https://github.com/koalaman/shellcheck/issues/809)) has been open for years with no implementation. Latest release v0.11.0 (2025-08-04).
- `shellcheck -s bash` on `cli/adc` is not a workaround: `${0:A:h}` and `${(j:, :)...}` are hard parse errors in bash grammar, not suppressible warnings.
- What zsh itself offers: `zsh -n` (NO_EXEC — "commands are read and checked for syntax errors, but not executed", [zsh options manual](https://zsh.sourceforge.io/Doc/Release/Options.html)). Verified locally on zsh 5.9: `zsh -n cli/adc` exits 0; a deliberately broken script exits 1 with a diagnostic. `zcompile` also fails on syntax errors but adds nothing over `-n`. There is no real third-party zsh linter (zsh-syntax-highlighting is interactive-prompt highlighting only, [per its README](https://github.com/zsh-users/zsh-syntax-highlighting/blob/master/README.md)).
- shellcheck still earns its place for the repo's bash/sh files: `.github/scripts/smoke-test.sh` and `images/base/claude-bootstrap.sh`.

### bats-core and zsh unit testing

- [bats-core](https://github.com/bats-core/bats-core/releases) v1.14.0 (2026-07-21), actively maintained. bats tests are bash, but [`run`](https://bats-core.readthedocs.io/en/stable/writing-tests.html) "invokes its arguments as a command" — any executable — so black-box tests of a zsh CLI are first-class: `run zsh cli/adc init --bogus` then assert `$status` / `$output` / `$lines` (plus `run -N` expected-status and `run !` negation). Host-safe surface for `adc`: `init` (template write, `--force`, placeholder substitution), `doctor` on the host path, usage/exit codes for unknown commands; `sync`/`apply`/`upgrade` self-guard with `require_container`, so their refusal message is itself testable.
- Helper libs bats-support/bats-assert are officially maintained; in GitHub Actions the official [bats-core/bats-action](https://github.com/bats-core/bats-action) (v4.0.0, 2026-02-08) installs bats plus the helper libraries in one step.
- zsh-native frameworks are not competitive: [zunit](https://github.com/zunit-zsh/zunit) is dead (last release v0.8.2 in 2018, last push 2023); [zsh-test-runner](https://github.com/olets/zsh-test-runner) is a niche micro-project; [shunit2](https://github.com/kward/shunit2) claims zsh support "since 2.1.2" with `shwordsplit` caveats but its last release is 2020. Since the tests here are CLI black-box (spawn `zsh adc ...`, assert output/exit/files), nothing zsh-native is needed — bats is the maintained choice.

### sheldon / starship config checks (verified locally)

- `sheldon lock` fully validates `plugins.toml` — the docs describe it as "installs the plugin sources and generates the lock file" ([CLI docs](https://sheldon.cli.rs/Command-line-interface.html)); there is no validate/verify subcommand. Verified locally (sheldon 0.8.5, `--config-dir`/`--data-dir` pointed at scratch dirs): config loading happens **before** network I/O — malformed TOML fails with exit 2 offline, unknown keys print `WARNING: unused config key`, a plugin missing source fields fails with exit 2 — but with a *valid* config it proceeds to clone every plugin repo (6 clones, ~9 s here). So `sheldon lock` against a throwaway data dir is a real semantic check that also catches dead plugin URLs, at the price of network; plain TOML well-formedness (`python3 -c 'import tomllib,...'` / `taplo check`) is the offline fallback.
- `starship print-config` parses the config and resolves it against starship's config model, warning on unknown keys — but **exits 0 even when the TOML fails to parse** (verified locally on starship 1.25.1: unparseable file → `[ERROR] ... Unable to parse the config file` on stderr, exit 0, falls back to defaults; unknown key → `[WARN] ... Unknown key`, exit 0; there is no `starship config validate`). A usable CI check must run `STARSHIP_CONFIG=dotfiles/starship.toml starship print-config` and fail on `ERROR`/`WARN` matches in stderr, not on exit code. Alternative with a true exit code: starship publishes a JSON schema (`https://starship.rs/config-schema.json`, referenced from the [config docs](https://starship.rs/config/)) usable via `check-jsonschema`/taplo after TOML→JSON conversion.

### devcontainer.json validation

- devcontainer.json is JSONC by spec ("a JSON with Comments file", [devcontainer reference](https://github.com/devcontainers/spec/blob/main/docs/specs/devcontainer-reference.md)), and `templates/devcontainer.json` carries comments — plain `jq` cannot parse it. `devcontainer read-configuration --workspace-folder <dir>` parses and resolves it, erroring on broken config (verified locally on 0.88.0 against the template, including its `<project-name>` placeholder — a valid string, so no pre-substitution needed).
- Official JSON schemas exist for stricter checking: [`devContainer.base.schema.json`](https://github.com/devcontainers/spec/tree/main/schemas) in the spec repo, linked from the [containers.dev JSON reference](https://containers.dev/implementors/json_reference/) — usable via ajv/`check-jsonschema` after comment-stripping. `read-configuration` is the lower-friction choice since the CLI is already a repo dependency.

## GitHub Actions runtime realities

- **arm64 hosted runners are free for public repos**: `ubuntu-24.04-arm` / `ubuntu-22.04-arm`, 4 vCPU / 16 GB / 14 GB SSD — identical specs to the x64 standard runners for public repos ([runners reference](https://docs.github.com/en/actions/reference/runners/github-hosted-runners)). Public preview 2025-01-16, GA 2025-08-07 ([changelog](https://github.blog/changelog/2025-08-07-arm64-hosted-runners-for-public-repositories-are-now-generally-available/)); since 2026-01-29 also usable in private repos at 2 vCPU ([changelog](https://github.blog/changelog/2026-01-29-arm64-standard-runners-are-now-available-in-private-repositories/)).
- **Standard runners cost nothing on public repos** (the arm64 GA changelog: "at no cost"; billing minutes apply to private repos); the Free plan's concurrency cap is 20 concurrent jobs on standard runners ([limits reference](https://docs.github.com/en/actions/reference/limits)).
- **buildx `type=gha` cache** ([docs](https://docs.docker.com/build/cache/backends/gha/)): backed by the Actions cache API (auth auto-wired by docker/build-push-action), `mode=max` to cache all layers, per-image `scope` to avoid clobbering; repo cache is 10 GB with LRU eviction and 7-day expiry ([caching reference](https://docs.github.com/en/actions/reference/dependency-caching-reference)). `type=registry` (cache pushed to GHCR) avoids the 10 GB cap. Caveat for this repo: `publish.yml` deliberately builds uncached so weekly rebuilds pick up apt security updates — layer caching belongs in **PR/test builds only**, keyed so it never feeds the publish path.
- **QEMU vs native matrix**: Docker's own docs say emulation with QEMU "can be much slower than native builds, especially for compute-heavy tasks like compilation and compression or decompression", recommending "multiple native nodes or cross-compilation instead, if possible" ([multi-platform docs](https://docs.docker.com/build/building/multi-platform/)). The CI pattern is per-platform jobs on native runners whose partial images are merged into one manifest — docker's [GitHub Actions multi-platform guide](https://docs.docker.com/build/ci/github-actions/multi-platform/) now ships this as reusable "GitHub Builder" workflows whose default runner mapping "sends Linux Arm platforms to `ubuntu-24.04-arm`". devcontainers/ci's own [multi-platform doc](https://github.com/devcontainers/ci/blob/main/docs/multi-platform-builds.md) says the same: QEMU builds "will significantly increase build times over native", and points at hosted arm runners. With free arm64 runners there is no longer a cost reason to emulate in test jobs; QEMU remains defensible only in the existing all-in-one publish build if its duration stays tolerable.
- Duration shape for this repo: tier 1 is seconds; tier 2 is dominated by the image build (unless it tests the published image, as today); tier 3 adds `devcontainer up` (image pull + DinD feature entrypoint + onCreate bootstrap) — minutes, not seconds, so per-PR tier 3 wants the gha-cached build or the `:latest` published image rather than a cold multi-arch build.

## Recommendations

| Tier | Recommendation | Runner shape |
| --- | --- | --- |
| 1 | `zsh -n` + bats-core black-box tests for `adc`; `devcontainer read-configuration` for all devcontainer.json files; `starship print-config` stderr-gated; `sheldon lock` in scratch dirs (accepts network) | one `ubuntu-latest` job, every PR |
| 2 | Keep and extend the plain `docker run`/`docker inspect` script (current `smoke-test.sh`); no CST, no goss | matrix `{base,node}` × `{ubuntu-latest, ubuntu-24.04-arm}`, native per arch |
| 3 | `devcontainer up` + `devcontainer exec` directly (no devcontainers/ci action), running a vendored `check`/`reportResults` checklist inside the live container | `ubuntu-latest` (+ arm optional), on main / nightly / release, not every PR |

**Tier 1 — `zsh -n` + bats-core for the CLI; shellcheck only where it applies; skip zunit.** shellcheck cannot see zsh at all (SC1071, open-by-design), and zunit is abandoned — the maintained combination is `zsh -n cli/adc adc.plugin.zsh` for syntax, shellcheck for the repo's actual bash files (`smoke-test.sh`, `claude-bootstrap.sh`), and bats-core (installed via `bats-core/bats-action`) driving `run zsh cli/adc ...` black-box tests of `init`/`doctor`/usage/`require_container` refusals. Config checks: `devcontainer read-configuration` per devcontainer.json, `starship print-config` gated on stderr `ERROR|WARN`, TOML parse for `plugins.toml` offline plus `sheldon lock` (scratch data dir) as the network-tolerant deep check — either inside tier 1, accepting ~10 s of clones, or folded into tier 2 where the network is already in play. Everything here runs in seconds on one `ubuntu-latest` job.

**Tier 2 — plain script, upgraded, not a new tool.** container-structure-test is in stated maintenance mode and its label assertions are string/regex-only — worse than the existing `docker inspect | jq` for `devcontainer.metadata`; goss is fast and maintained but blind to image metadata and adds per-arch binary bookkeeping. The existing script already expresses every needed check in the language contributors know. Upgrade path instead of tool swap: split checks into small functions with a `check`-style accumulator (same vocabulary as tier 3), run the matrix natively on `ubuntu-24.04-arm` for the arm64 image (free, GA), and keep `docker inspect` + `jq` as the metadata oracle. Revisit goss only if the checklist grows past ~30 checks and junit reporting becomes wanted.

**Tier 3 — devcontainer CLI directly, upstream test-project idiom.** This is the only tier that exercises the baked `devcontainer.metadata` (volumes, onCreate bootstrap, DinD) and the template as users consume it — exactly how devcontainers/images and devcontainers/templates test theirs. Use `adc init` into a temp project (testing the CLI's real entry point for free), `devcontainer up --id-label`, `devcontainer exec` a vendored ~30-line `test-utils.sh` with `check`/`reportResults`, then `docker rm -f` by label. Skip the devcontainers/ci action: it wraps the same commands with less control and this repo already drives the CLI directly in `publish.yml`. Run on main + weekly (aligned with the publish cadence) rather than every PR; a PR-triggered variant can point the template at a locally built single-arch image via `configFile` override.
